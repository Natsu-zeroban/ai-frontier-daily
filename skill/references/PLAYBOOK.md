# PLAYBOOK.md — 运营手记

四份 reference 的分工：
- **STYLE.md** — 怎么写（写作与呈现铁律、冷读者复读）
- **TEMPLATE.md** — HTML 怎么改（片段、归档、发布 checklist）
- **INSIGHTS.md** — 读日报文章学到的、能改进「自己怎么干活」的通用洞见
- **PLAYBOOK.md（本文件）** — 运营这个日报本身踩过的坑和形成的判断：分类怎么定、立场怎么标、难抓的链接怎么办、串读怎么写、发布怎么不翻车

这些是 20 期攒下来的操作经验，接手的人先读一遍能少走很多弯路。

---

## 一、分类判断：干货精读 / 要闻茶点 / 轻精读

- **判据**：对"学怎么用好 AI 的人、三个月后还有价值"→ 干货精读；"知道有这回事就够"→ 要闻茶点。
- **同一产品/主题反复出现**，按"这次有什么新信息"分档，别重复灌：首次亮相惊艳 → 精读；纯开源/发布公告 → 茶点；技术答疑/深度但受众窄 → 轻精读 + 标注受众。（实例：某视频模型三次出现，分别按「横测精读→开源茶点→技术 AMA 轻精读」处理。）
- **技术密度极高的文章**（架构 AMA、模型内部原理）：核心只讲"对读者有操作价值的部分"，硬核细节压进延伸块并标「开发者向/做部署研究再看」，绝不整段搬架构黑话。
- **超长文**（几万字趋势报告）：只提炼对读者最有用的 2–3 块，不追求覆盖所有章节——能力上做减法。

## 二、立场标注（关乎可信度，别漏）

- **厂商为自家产品发的技术报告/评测、带推广性质的内测介绍**：必须在来源行如实标「带产品立场/偏正面」，并把"数据可信度"和"动机"分开说清（如：题目第三方出、方法可复算 → 数据可信；结尾在引流 → 动机打折看）。
- **个人重度用户的主观体验**：标「个人实测、主观」——框架和思路可借，绝对结论别当真。
- **时效性强的跑分/价格**：正文点趋势，具体数字压进延伸并标「看趋势别当定论，迭代以周计」。

## 三、抓取疑难（脚本之外的经验）

- **X/Twitter 长文**：`fetch_article.py` 和 WebFetch 都抓不全，用镜像接口 `https://api.fxtwitter.com/<user>/status/<id>`，从返回 JSON 的 `tweet.article.content.blocks` 取全文（比常规正文接口完整得多）。
- **纯前端渲染的作品/项目页**（打开一片加载占位、curl 和 WebFetch 只拿到导航壳）：通常只能拿到标题/描述（og:meta）。这类"作品链接"适合做**茶点一句话**——基于能确认的信息写、不编造细节；要深入就让用户贴内容。
- **微信图片型推文**：正文藏在页面 description 里，脚本已兜底提取。

## 四、串读与编排

- **每期结尾的「串读」**：找两篇（或本期与往期）的共同线索，落到一句**对读者可操作**的话，别空泛抒情。
- **攒够期数后主动做跨期呼应**（某期观点在早期哪一期出现过）——让日报显得是一个活的知识体，而不是流水账。
- **期主题命名**：短、抓人、概括当期共性；tab 副标同理。

## 五、发布不翻车（补充 SKILL 工作流的细节）

- 打开线上用**正确域名 + 防缓存参数**（`?v=时间戳`）；域名务必核对，手滑打错会打开一个不存在的站。
- Windows 下 git 的 `LF→CRLF` warning 是正常现象，忽略即可。
- **第 6 步反哺宁缺毋滥**：判断这期文章对"怎么干活"没有可操作增量时，就不加（纯发布/趋势观察类几期都没加）——不加本身就是收录标准在起作用，别为凑而凑。

## 六、维护者的自我提醒

- **长会话 / 多步骤重复任务里，警惕"描述而非执行"的空转**：想到要调用某个工具时，直接调用，不要反复叙述"我要调用它"。一旦发现自己在重复同一句意图，立刻把下一个动作变成真正的工具调用。
- **每期节奏固定**（照 SKILL 六步走），靠固定流程对抗"每次重新发明一遍"的消耗。
